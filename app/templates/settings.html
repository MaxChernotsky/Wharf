Prep an existing tool with AI

Make this project ready to run inside Wharf, a dashboard that hosts many small web tools as supervised subprocesses. Requirements:

1. The web server must bind 0.0.0.0 (never 127.0.0.1/localhost) and take its port from the PORT environment variable, with a sensible fallback for local dev. Wharf also supports a {port} placeholder in the run command if a CLI flag is easier.
2. All dependencies must be declared: requirements.txt or pyproject.toml for Python (runs on Python 3.12), package.json (plus a lockfile if possible) for Node (runs on Node 22). No globally installed packages.
3. Handle SIGTERM by shutting down cleanly and promptly.
4. Use only relative paths from the project root (the working directory is always the tool's own folder). Write any persistent data inside the project folder.
5. Do not assume a GPU, a browser, or an interactive terminal.
6. Create a tool.yml in the project root:

name: <Display Name>
description: <one line>
icon: "<a single emoji>"
type: python            # python | node | custom
install: <install command, e.g. "uv pip install -r requirements.txt" or "npm ci">
run: <start command; use {port} for the port, e.g. "streamlit run app.py --server.port {port} --server.address 0.0.0.0 --server.headless true">
autostart: false
restart: on-failure     # never | on-failure | always
health:
  type: http            # tcp | http | none
  path: /
  timeout_s: 120        # allow extra time if models load at startup
idle_stop_minutes: 0    # optional: stop after N min with no connections (0 = never)
max_memory_mb: 0        # optional: restart if RSS exceeds this (0 = unlimited)

7. After every edit to this project (including edits that come later, not just this
   first pass), (re-)create a zip of the project root ready for Wharf's "Add a tool
   — upload a zip" flow: include tool.yml and all source/dependency-manifest files,
   but exclude .git, .venv, node_modules, __pycache__, and any other build/dependency
   output — Wharf installs dependencies itself from a clean checkout. Name it
   <tool-folder-name>.zip and put it in the project root (or its parent) so it's easy
   to find. If the project root ends up nested one level inside the zip, that's fine —
   Wharf unwraps a single top-level folder automatically.

Notes: Wharf injects PORT, HOST=0.0.0.0, TOOL_NAME and TOOL_DIR into the environment, prepends the project's .venv/bin (Python) or node_modules/.bin (Node) to PATH, and runs the install command from the project root. Environment variables listed under env: in tool.yml also support the {port} placeholder. Wharf also exposes a notification relay: from inside the tool, POST http://localhost:8080/api/tools/$TOOL_NAME/notify (8080 is Wharf's own dashboard port, reachable from every tool over loopback) with a JSON body of {"message", "title"?, "priority"?, "data"?, "device"?, "devices"?} sends a push notification via Home Assistant if the user has configured one or more devices (Settings → Notifications). By default it goes to this tool's notify_devices (set in tool.yml) or the Settings-page default; pass "device" (one id) or "devices" (a list of ids) in the request to target specific device(s) for that call instead. Use it for things worth telling the user about — a long job finishing, an error needing attention — but don't assume it's configured (treat a non-2xx response as informational, not fatal) and never block the tool's own startup or main request path on it.

After making the changes, verify the server starts, binds 0.0.0.0 on $PORT, and exits cleanly on SIGTERM — then create the zip per step 7.

Tool port range

Hosted tools are assigned ports from this range (a pinned port: in a tool's manifest always wins; everything else gets a sticky auto-assigned port from here). Saving stops and restarts any tools that are currently running so they come back up inside the new range — tools that are stopped just get renumbered next time they start.

This only changes what Wharf assigns inside the container. For tools to stay reachable from outside, the range must still be mapped 1:1 in your Docker/Unraid port mapping (e.g. -p {{ settings.tools_port_range }}:{{ settings.tools_port_range }}) — update that separately if you widen or move the range.

Tools report notifications to Wharf with POST /api/tools/<id>/notify — Wharf relays each one to one or more Home Assistant notify services ("devices" below), which is what's actually configured to reach a phone (typically a mobile-app notify service HA sets up per device). Find a service name in HA under Developer Tools → Actions, searching for notify. — use the part after the dot. Add a row per phone/device Wharf should be able to reach, and check Default for the one(s) that get a notification when a tool doesn't say otherwise — each tool can also pick its own device(s) on its detail page, and a single notify call can target a device directly.
